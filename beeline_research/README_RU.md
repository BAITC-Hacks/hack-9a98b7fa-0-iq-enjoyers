# ProfitPilot: исследование для кейса Beeline

Дата проверки: 23 сентября 2026. Рекомендация — агент, который адаптивно проводит
пилоты и формирует портфель тарифных кампаний по ожидаемому чистому приросту ARPU.

адаптивная эвристика реализована как эксперимент и пока уступает ему.
`submission.csv` создан локально официальной программой и не включён в GitHub.

## Основание и поправки к прежнему совету

Изучены присланное ТЗ, публичный `PARTICIPANT_GUIDE.md`, `agent_template.py`
и разрешённые таблицы из
[пакета участника](https://drive.google.com/file/d/1cQUKtE_cm9TVXgzpcFwQYYUpmuFaJHHT/view).
Четыре присланных текста ТЗ совпадают. Другой Drive-файл — PDF руководства.
Внутренние реализации среды и скрытые эффекты не исследовались.

Этот кейс требует оптимизации тарифных маркетинговых кампаний. Прежний список
NOC, покрытия и энергосбережения не задаёт решение этого ТЗ. В ТЗ указаны **9 часов**,
а прежняя оценка «5 часов на MVP» была взята из общей программы мероприятия.

Проверяемые требования:

| Требование | Значение |
|---|---|
| Интерфейс | `agent.py`, `class Agent`, `act(self, env) -> list[dict]` |
| Кампании | от 1 до 10; существующий `target_tariff` и `channel` |
| Размер кампании | не более 5 000 абонентов |
| Контакты | не более 15 000, включая пилоты |
| Бюджет | 100 000 у.е., включая пилоты |
| Пилоты | более 0, максимум 20; размер 10–200 |
| Каналы и цена контакта | push 0; sms 4; digital_ads 22; call 160 |
| Итог | `submission.csv` через `make_submission.py` |
| Проверка | `local_eval.py`, затем `local_eval.py --runs 10` |

В ТЗ LLM в принятии решений опциональна. Если используется предоставляемый жюри
ключ, он читается из `OPENAI_API_KEY`. Участие GLM через NVIDIA в исследовании
не означает, что такой ключ или endpoint будут доступны на судействе.
Общие правила мероприятия следует отличать от требований отдельного кейса.

Есть противоречие в самом пакете: руководство допускает 10 минут на агента и
LLM-вызовы, а комментарий шаблона говорит о 5 минутах и работе без интернета.
Практичный выбор — локальное численное ядро, которое работает быстрее 5 минут,
и необязательный LLM-вызов с тайм-аутом и запасной логикой. Актуальную трактовку
интернет-доступа и лимита времени нужно сверить с организаторами.

## Что действительно обнаружено в данных

Подсчёт сделан по CSV, а не по описанию кейса:

- `customer_profile.csv`: 23 441 строка, идентификаторы не дублируются.
- Сумма `predicted_arpu`: примерно 150 641 084,25 у.е.
- `data/change_tariff.csv`: **14 823 записи** без заголовка; в ТЗ написано 14 824.
- У 95 абонентов пустой `current_tariff`; у 5 пустой `arpu_segment`.
- В 1 407 исторических строках `AVG_ARPU_PREV_3M <= 0`.
- Идентификаторы исторической выборки и целевой аудитории не пересекаются.
- 63 непустые ячейки `current_tariff × arpu_segment` с валидным тарифом
  и сегментом; крупнейшая содержит 4 726 абонентов.
- В истории есть дата, ID, исходный и целевой тариф, ARPU до и после.
  Отдельной колонки канала, контрольной группы и рандомизации в этой таблице нет.

Следствие: сначала обработать пропуски и недопустимые знаменатели. Историю
использовать для предварительного ранжирования и слабых априорных оценок.
Не объявлять обычную разность ARPU причинным uplift. Точный переход
из исторических агрегатов к текущим сегментам требует явных предположений.

## Свежие исследования и применение

Это отобранные релевантные работы, а не утверждение об исчерпывающем поиске.
Ссылки, даты версий и ограничения также находятся в `sources.json`.
Предлагаемое применение к кейсу — инженерный вывод, не экспериментальный результат.

| Работа | Дата / статус | Что использовать |
|---|---|---|
| [Budget-Constrained Causal Bandits](https://arxiv.org/abs/2604.26169v2) | версия 28.08.2026; препринт | Одновременное обучение эффектам, выбор экспериментов и распределение бюджета. В кейсе перенести принцип на пакетные пилоты. |
| [Multi-channel Uplift Policy Learning](https://arxiv.org/abs/2607.28182) | 30.07.2026; препринт | Оценивать выбор каналов совместно с бюджетом. Простая сортировка по коэффициенту эффективности недостаточна. |
| [Evaluating Uplift Modeling under Structural Biases](https://arxiv.org/abs/2603.20775v2) | версия 16.06.2026; в записи указано принятие KDD 2026 | Отделять качество прогноза от качества решений; проверять устойчивость при смещениях данных. |

| [Bi-Level Decision-Focused Causal Learning](https://arxiv.org/abs/2510.19517) | 22.10.2025; NeurIPS 2025 | Совмещать историю и экспериментальные данные, оптимизируя качество решений. Полная нейросетевая реализация из статьи — после MVP. |

Данные и постановки в этих работах отличаются от синтетического кейса Билайна.
Чужие проценты улучшения нельзя обещать для нашей системы. Работы по причинной
оценке требуют условий идентифицируемости и данных, которых текущая таблица может
не содержать. Пилотное API — основной разрешённый источник информации о текущей аудитории.

## Предлагаемая архитектура

`история → гипотезы → выбор пилота → результат → обновление оценки → портфель → проверка лимитов`

1. **Кандидаты.** Создать непересекающиеся сегменты по текущему тарифу и ARPU.
   Для каждого рассмотреть несколько целевых тарифов с учётом истории и пакетов.
   Пропуски обработать явно, не превращать их в невалидный фильтр. Большой сегмент
   делить только доступными в API фильтрами, если это потребуется на другой базе.
2. **Слабый исторический prior.** Оценить относительное изменение для исторических
   переходов с положительным исходным ARPU, использовать shrinkage к более общей
   оценке для редких переходов. Отдельно учитывать наблюдения с нулём/отрицательным
   знаменателем; не маскировать их делением на произвольный epsilon.
3. **Пилоты.** Выбирать гипотезы с учётом потенциального дохода, неопределённости
   и стоимости проверки. Начальная проба 30–50 человек — предлагаемая эвристика,
   не требование. Перспективные и неопределённые варианты проверять дополнительными
   пилотами, например 100–200 человек. Все размеры ограничить доступной аудиторией,
   бюджетом и контактами. Числа проверить сравнением стратегий по нескольким seed.
4. **Обновление.** `agent_template.py` показывает `res['observed_lift_ratio']`.
   Другие поля результата и точную семантику нормировки каналом нельзя выдумывать.
   Калибровать неопределённость по документированной информации и повторным
   пилотам; учитывать, что пересекающиеся выборки не обязательно независимы.
   Для адаптивно выбранных победителей обычный интервал после отбора может быть
   излишне оптимистичен; предусмотреть независимую повторную проверку кандидата
   или последовательный метод оценки.
5. **Портфель.** Для MVP выбрать максимум один вариант на непересекающуюся ячейку.
   Оптимизировать ожидаемый чистый прирост с ограничениями на остаток бюджета,
   контакты и число кампаний. Начать с жадного выбора и локальных замен, затем
   сравнить с OR-Tools. Пилоты уже тратят ресурсы и уже дают эффект: исключить
   повторное суммирование их дохода, учитывать пересечения с финальными контактами.
6. **Роль LLM.** Получает агрегаты и список допустимых кандидатов, предлагает следующую
   гипотезу или выбирает из разрешённых идентификаторов. Код проверяет решение,
   считает бюджет и вызывает `env.run_pilot`. При ошибке модели работает та же
   численная стратегия. Отчёт объясняет выбор через результаты пилотов.

Ориентир для одиночной кампании на непересекающемся сегменте:

```text
estimated_net_gain = sum(predicted_arpu_i * estimated_lift_i_for_this_channel)
                     - number_of_contacts * channel_cost
```

`estimated_lift` здесь уже соответствует конкретному каналу: нельзя повторно
умножить его на эффективность канала, если она включена в возвращаемый эффект.
Для пересекающихся кампаний доход учитывается по лучшему эффекту на абонента,
а оплачиваются все контакты; простая сумма доходов кампаний неверна.
Не предполагать, что среда бесплатно отменяет отрицательный эффект кампании.

В качестве консервативного внутреннего критерия можно использовать
`expected_gain - lambda * uncertainty`, но коэффициент и способ оценки
неопределённости должны проверяться экспериментально. Оптимизировать нужно деньги,
а не долю переходов и не только средний процент uplift.

Пример различия каналов (выдуманные числа): при ARPU 6 000, оценке эффекта
push 2% и sms 2,6% ожидаемый результат равен 120 и 152 у.е. на контакт.
Бесплатный push не обязательно лучший. Но он тоже расходует лимит контактов,
а при отрицательном эффекте может снизить доход даже без денежной стоимости.

Если уверенно прибыльных кампаний нет, агент всё равно должен вернуть хотя бы
одну корректную по ТЗ: выбирать наименее рискованный допустимый вариант после
пилотов и явно отмечать неопределённость. Положительный результат не гарантирован.

## GitHub: что переиспользовать

- [google/or-tools](https://github.com/google/or-tools): оптимизация набора кампаний
  под бюджет, контакты и число кампаний. Учёт пересечений нужно описать в модели.
- [fidelity/mabwiser](https://github.com/fidelity/mabwiser): примеры bandit-политик
  для выбора эксперимента. Готового решения наших ограничений там нет.
- [uber/causalml](https://github.com/uber/causalml): uplift и несколько воздействий,
  когда появятся корректные экспериментальные данные. Для ARPU нужен метод,
  поддерживающий непрерывный исход.
- [py-why/EconML](https://github.com/py-why/EconML): оценка неоднородных эффектов
  и policy learning при достаточных данных и выполнении причинных предположений.

Начальный стек: Python, pandas/numpy, простые статистические оценки; оптимизатор
добавлять после рабочего baseline. GitHub-токен для просмотра этих репозиториев
не нужен. Версии библиотек зафиксировать после успешного воспроизведения.

## План на девять часов и проверка

1. **0–1 ч:** данные, валидация полей, baseline из `agent_template.py`, первый прогон.
2. **1–3 ч:** кандидаты, исторические оценки, очистка данных, подсчёт размеров фильтров.
3. **3–5 ч:** адаптивные пилоты, неопределённость, сохранение остатка ресурсов.
4. **5–6,5 ч:** распределение бюджета по каналам и сборка корректного портфеля.
5. **6,5–7,5 ч:** необязательный LLM и журнал аргументов/пилотов.
6. **7,5–9 ч:** десять seed, CSV, README, короткая демонстрация.

Сравнить на одинаковых seed шаблон, фиксированные пилоты и адаптивную стратегию.
Показывать средний/минимальный чистый результат, разброс, долю отрицательных
прогонов, число отброшенных кампаний, время, бюджет и контакты. Сравнение без
пилотов допустимо только как исследовательская абляция, оно не проходит must-have.
Мок-результат не предсказывает скрытые эффекты жюри. Не подгонять к конкретным seed.

```bash
python3 local_eval.py
python3 local_eval.py --runs 10
python3 make_submission.py
```

Эти команды запускать в распакованном пакете после создания `agent.py`.
В присланной таблице критериев README/воспроизводимость дают 25 из 100 баллов,
столько же, сколько техническая реализация: документацию включить в план.

Формулировка новизны: «Агент выбирает не только кампании, но и следующие
эксперименты; переносит ограниченную информацию из истории, обновляет оценки
по пилотам и собирает портфель по ожидаемому чистому ARPU при совместных лимитах
бюджета, контактов и кампаний». Это комбинация известных методов под конкретное
ограничение, а не заявление о новом алгоритме.

## Рецензия через GLM-5.3

`review_with_glm.py` отправляет эту записку и `sources.json` модели через
NVIDIA endpoint. Он **не ищет в интернете** и не скачивает содержание ссылок:
источники выше уже найдены и проверены при подготовке записки. Ответ модели —
дополнительная рецензия, а не независимое подтверждение фактов.

```bash
cd /home/hilla/Downloads/github-project
python3 beeline_research/review_with_glm.py --dry-run
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
# Установите NVIDIA_API_KEY локально, затем:
.venv/bin/python beeline_research/review_with_glm.py
```

Ключ читается из `os.environ`, не из буквальной строки `"$NVIDIA_API_KEY"`.
[Ключи NVIDIA API](https://build.nvidia.com/settings/api-keys).
Ключ `bak-…` аутентифицирует Brev, это другой сервис:
[документация Brev](https://docs.nvidia.com/brev/guides/api-keys).
Раскрытые в чате ключи GitHub/Brev следует перевыпустить.

По рекомендации OpenAI Docs в SDK заданы тайм-аут и обработка ошибок, отключены
автоматические повторы. Это тайм-аут сетевого запроса, не глобальный таймер агента.
См. [ошибки SDK](https://developers.openai.com/api/docs/guides/error-codes)
и [настройку тайм-аута](https://developers.openai.com/api/docs/guides/flex-processing).
На момент подготовки NVIDIA API Key отсутствовал, поэтому GLM не вызывался.
